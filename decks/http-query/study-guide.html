Fixed terms in this guide

A hop is one system between the client and the origin: a CDN, a proxy, a WAF, a load balancer. The origin is the server that owns the resource. The query component is the part of a URI after ?. The query content is the body of a QUERY request. Safe and idempotent have the meanings in part 01.

The talk in 60 seconds

  1. The method tells every hop what the client wants to do. GET is safe and idempotent. POST is neither.
  2. GET puts the query in the URI. A long query hits length limits that the client cannot know. Logs, history and the Referer header keep URIs.
  3. POST puts the query in the body. But POST does not promise "safe". Thus caches and automatic retries do not work.
  4. HTTP had no standard method for "safe, idempotent, with the query in the body". RFC 10008 (June 2026) adds QUERY for this gap.
  5. A QUERY request must have a Content-Type. The server must not guess the type. Caches can keep responses, but the cache key must include the body.
  6. The server can give two URIs. Location: a GET runs the query again. Content-Location: a GET returns this result again.
  7. Security: safe is not secure. The body is still untrusted input. Caches must key on the body. Browsers always send a CORS preflight. Signatures must cover Content-Digest.
  8. Deployment: every hop must know QUERY. One hop with no support breaks the request. One hop with weak rules makes a bypass.
  9. Conclusion: QUERY does not replace GET or POST. Its security depends on the implementation, not on the method.

Answers at three lengths

10 seconds

QUERY is a new HTTP method. It is safe and idempotent, the same as GET. But it sends the query in the body, the same as POST.

30 seconds

GET puts the query in the URI. Long queries break, and logs keep them. POST puts the query in the body, but it does not promise "safe". Thus caches and retries do not work. RFC 10008 adds QUERY: a safe, idempotent request with the query in the body. Caches can keep its responses, and the server can give the query its own URI.

2 minutes

Start with the 30-second answer. Then add the rules: Content-Type is mandatory, and the server must not guess the type. A wrong type gets 415, and a query that the server cannot run gets 422. The cache key must include the body. Location gives a URI that runs the query again. Then the security points: safe is not secure, so injection and authorization stay the same. A cache that ignores part of the body can send one user's results to another user. Browsers always send a CORS preflight. A signature must cover Content-Digest, because @query is empty. End with deployment: every hop must support QUERY, and its security depends on the implementation.

RFC 9110 calls the method "the primary source of request semantics" Source RFC 9110 §9.1. Each hop reads the method to know what the client wants to do.

Safe and idempotent

Safe (RFC 9110 §9.2.1)

The client does not ask for a change of state on the server. Thus a cache, a prefetcher, a crawler or a link preview can send the request with no risk to the user.

The server can still log the request, count it or charge for it. The client did not ask for these effects, so the method stays safe.

Idempotent (RFC 9110 §9.2.2)

One request and ten identical requests have the same intended effect. Thus a client can send the request again after a connection fails. It does not need to know if the first one arrived.

"A proxy MUST NOT automatically retry non-idempotent requests." All safe methods are also idempotent.

Source RFC 9110 §9.2 and §9.3; RFC 10008 §5.1 for QUERY. The IANA method registry lists the safe and idempotent values of each method.

Safe is a promise about intent

The definition of safe "does not prevent an implementation from including behavior that is potentially harmful" Source RFC 9110 §9.2.1. If a safe method can start an unsafe action, for example GET /item?do=delete, then "the resource owner MUST disable or disallow that action".

Method names are case-sensitive

RFC 9110 §9.1 says that the method token is case-sensitive. Thus QUERY and query are two different methods. All registered methods are upper case.

The Fetch standard changes only six names to upper case: DELETE, GET, HEAD, OPTIONS, POST and PUT Source Fetch, normalize. With method: 'query', fetch() sends query. Node 24 replied 400 to a lower-case query request Tested.

02 The problem that QUERY solves

This part answers the question "why a new method?". There are three problems: length, exposure, and a gap in the method table.

Problem 1: the URI gets too long

A search with many filters makes a long URI. Slide 6 shows one. The server replies 414 URI Too Long Deck.

GET /search?q=laptop&brand=lenovo,dell,hp&price_min=40000&price_max=100000&ram=16,32&sort=price&page=2&filters=%7B%22gpu%22%3A%5B%22rtx-4060%22%2C%22rx-7600%22%5D%7D HTTP/1.1
Host: shop.example

HTTP/1.1 414 URI Too Long
  • No fixed limit. "It is RECOMMENDED that all senders and recipients support, at a minimum, URIs with lengths of 8000 octets" Source RFC 9110 §4.1. This is a minimum, not a maximum.
  • Unknown limits. The request goes through many systems. Each one can have a different limit, and the client cannot know them before it sends the request Source RFC 10008 §1.
  • Encoding cost. Some characters must be percent-encoded. Each one becomes three characters.
FormTextLength
JSON filter{"gpu":["rtx-4060","rx-7600"]}30
encodeURIComponent()%7B%22gpu%22%3A%5B%22rtx-4060%22%2C%22rx-7600%22%5D%7D54

Twelve characters change: { } [ ] : , and six quotes. Each adds two characters, so 30 + 24 = 54 Tested with Node.

Problem 3: a gap between GET and POST

Query input in the URIQuery input in the content
Safe and idempotentGET gets a resource; the query is part of the URIEmpty before RFC 10008. Now QUERY
Not safeGET /item?do=delete: bad practice; the owner must disallow itPOST: the resource decides what to do with the content

POST for a query "hinders caching and uses an unsafe method for what would otherwise be a safe request."

RFC 9110 §17.9

Why not GET with a body?

"Content received in a GET request has no generally defined semantics." A client "SHOULD NOT generate content in a GET request" unless the origin server said that it supports it Source RFC 9110 §9.3.1.

Some hops drop the body. Some reject the request. If two hops disagree about the body, request smuggling becomes possible Analysis.

Why not POST?

POST is not safe and not idempotent. A proxy must not send it again automatically. A cache can use a POST response only for a later GET or HEAD Source RFC 10008 Table 1.

Also, WAF and CSRF rules treat POST as a write. A read-only search then gets the same controls as a payment Analysis.

The one-line answer

GET has the right meaning in the wrong place. POST has the right place with the wrong meaning. QUERY has the right meaning in the right place.

The definition

QUERY asks the target resource to process the content of the request in a safe and idempotent way, and to send back the result Source RFC 10008, Abstract and §2. The client can send the request again or start it again after a failure, and no partial change of state can occur.

  • The target URI sets the scope. QUERY /contacts queries the contacts.
  • The content is the query. Its format comes from Content-Type.
  • A query component in the target URI is allowed. Its effect is specific to the resource (§2).

"Potentially no" means: one POST endpoint can be harmless, but the method promises nothing Deck.

Rules for the request content (§2, §2.1)

MUST or "is appropriate"?

Two rules are mandatory. A server MUST fail a request with a missing or inconsistent Content-Type, and the problem "MUST be rejected with a 4xx" response. A server "is not allowed to infer a media type from the request content". The exact codes 400, 415, 422 and 406 are the RFC's recommendations ("is appropriate", "can be used") Source RFC 10008 §2, §2.1.

Why no guessing? Content sniffing lets an attacker make the server read the body as a different format. The client and the server then disagree about the query Analysis.

The Accept-Query header (§3)

  • A response header. It says: this resource supports QUERY, with these query formats.
  • It is a Structured Field (RFC 9651): a List of Tokens or Strings. Each item is a media range. Media type parameters become Structured Field parameters.
  • Wildcards: only */* and type/*. The order of the items is not significant.
  • It applies to all URIs with the same path. The query component is ignored.
Accept-Query: "application/jsonpath", application/sql;charset="UTF-8"

Security rule for these URIs (§4)

If the query has sensitive information, the new URI "SHOULD be chosen such that it does not include any sensitive portions". If the server puts the query into the URI, the data goes back into the logs.

Analysis server.mjs uses a counter: /contacts/stored-queries/1, /2, /3. Another client can guess these URIs and run a query that it did not write. A real server must link each stored query to its owner, check authorization on the GET, or use an unguessable ID.

Redirects (§2.5)

StatusTypeWhat the client does
301, 308permanentsends the QUERY again to the new URI
302, 307temporarysends the QUERY again to the new URI
303See Othersends a GET to the Location URI (an "indirect response", App. A.4.3)

Old browsers change POST to GET after a 301 or 302. RFC 10008 says that this exception does not apply to QUERY Source §2.5.

Conditional and range requests (§2.6, §2.8)

  • Conditional. The selected representation of a QUERY is the same as for a GET to the equivalent resource. Thus ETag, If-None-Match and 304 Not Modified work. App. A.5 shows this with XSLT and SQL queries.
  • Range. Range requests work the same as for GET. But byte ranges are of little use for query results. The RFC expects the paging of the query format, for example SQL FETCH FIRST.

Caching (§2.7)

  • "The response to a QUERY method is cacheable; a cache MAY use it to satisfy subsequent QUERY requests".
  • "The cache key for a QUERY request ... MUST incorporate the request content" and its related metadata, for example Content-Type.
  • Caches MAY remove differences that do not change the meaning: content encodings, or format rules such as those of +json types. This normalisation is only for the key. The cache must not change the request that it forwards.
  • A client can send Cache-Control: no-transform. It is advisory.

Part 05 explains the risk of a wrong normalisation.

IANA registration (§5)

RegistryEntryValues
HTTP Method RegistryQUERYSafe: yes. Idempotent: yes. Reference: §2.
HTTP Field Name RegistryAccept-QueryStatus: permanent. Structured type: List. Reference: §3.

Why the name QUERY (Appendix B)

The method registry already had three safe, idempotent methods with a body: PROPFIND (RFC 4918), REPORT (RFC 3253) and SEARCH (RFC 5323). The early drafts used SEARCH. The authors chose QUERY for three reasons:

  1. The other methods use a generic media type (application/xml) for the content. QUERY gets its meaning only from the content type.
  2. All three come from WebDAV, and many developers have mixed feelings about WebDAV.
  3. "QUERY" maps well to the query component of the URI.

Cache risks

Caches can keep QUERY responses. This is an advantage. It is also the largest new attack surface Deck.

  • The rule. The key MUST include the content and its metadata. Normalisation is allowed. A wrong normalisation gives wrong responses Source RFC 10008 §2.7, §4.
  • Old caches. Many caches use only the method and the URI as the key Source RFC 9111 §2. A cache that does not know QUERY must not store its responses at all.
  • Authenticated requests. A shared cache must not use a stored response to a request with Authorization for other requests, unless the response allows it (for example public or s-maxage) Source RFC 9111 §3.5.
  • Cache-poisoned denial of service Analysis. Nguyen et al. (2019) made the origin return an error with a header that the cache ignores. The cache stored the error. For QUERY, the attacker can send the same body as a popular query, and add such a header. The cache can then keep the error under the key of the popular query.
  • Web cache deception Analysis. Mirheidari et al. (2020) made caches store private pages through path confusion. The result URIs of QUERY (Content-Location) hold private results. Send Cache-Control: private or no-store for them.
Defences for caches
  • Key on the method, the target URI, Content-Type and the full content.
  • Normalise only what you understand. If you are not sure, do not normalise.
  • Send Cache-Control: private for results that are specific to one user.
  • Give a Location. Then shared caches can use a plain GET, which they handle well.
  • Test: send two queries that differ in one field, and check that the second one is not a cache hit.

Browsers and CORS

The good news

A malicious page cannot send QUERY to your API without your permission in a preflight. A form can send a cross-site POST with no preflight. Thus QUERY has stronger protection than POST Deck.

The risk that stays

QUERY is safe, so a forged QUERY must not change anything. The real risk is reading. If the server reflects any Origin and sends Access-Control-Allow-Credentials: true, any page can read the user's results. Chen et al. (2018) found that CORS is often configured incorrectly.

  • Use an allow-list of origins. Do not reflect the Origin header when you allow credentials.
  • Send Vary: Origin when the response depends on the origin.
  • Expose only the headers that the page needs, for example Location.
  • Set Access-Control-Max-Age so that the browser does not send a preflight for each request.

  • RFC 9421 "does not provide coverage for the content of an HTTP message under the signature". Sign the Content-Digest field. The verifier must calculate the digest again over the bytes that it got Source RFC 9421 §7.2.8.
  • Some frameworks merge URI parameters and form parameters in the body. An attacker can then "shadow or replace" a signed parameter with an unsigned one Source RFC 9421 §7.5.8. QUERY content can be form-encoded.
  • A signature gives integrity and origin. It does not give authorization or confidentiality.

The verifier, step by step Analysis

  1. Check that the signature covers @method, @target-uri, content-type and content-digest.
  2. Calculate the SHA-256 of the body that arrived. Compare it with Content-Digest.
  3. Verify the signature with the key of keyid.
  4. Check the created time, to limit replay.
  5. Read the query from one place only: the body.

Request smuggling and body framing Analysis

  • HTTP/1.1 finds the end of a body with Content-Length or with chunked Transfer-Encoding Source RFC 9112 §6.
  • A hop that does not know QUERY can reject it (405 or 501). Or it can handle the body in a different way from the next hop.
  • When two hops disagree about where a request ends, an attacker can hide a second request in the body. T-Reqs found such differences between pairs of real servers (Jabiyev et al., 2021).
  • Defence: test QUERY with a body through every hop. Reject requests that have both Content-Length and Transfer-Encoding. Use HTTP/2 between hops where possible.

WAF rules

  • OWASP test case WSTG-CONF-06 tests HTTP methods. It includes method tampering to get around access control Source OWASP.
  • A WAF that examines only POST bodies lets QUERY bodies through with no check. A rule that finds SQL words in a GET URI does not see the same words in a QUERY body Analysis.
  • Add QUERY to the body rules. Use the same size limits as for POST. Allow QUERY only on the routes that support it.

Logs and monitoring Analysis

  • A log parser that expects only the classic methods can drop QUERY lines, or give them the wrong label.
  • Do not log raw query bodies with personal data. Log the stored-query ID or a hash of the body, and its size.
  • Watch the rate of 405 and 415 replies. A sudden increase can show a scan or a broken client.

Is QUERY more secure than GET?

BetterThe sameNew work
  • The input is not in the URI. Fewer copies in logs, history and Referer.
  • A cross-site page cannot send it without a preflight.
  • Reads no longer need an unsafe POST.
  • Injection, authorization, cost, disclosure.
  • Bodies can still be logged.
  • TLS is still necessary.
  • The cache key must include the body.
  • Every hop must support QUERY.
  • Signatures need Content-Digest.
  • Stored-query URIs need access control.
The short answer

Not by itself. QUERY decreases one exposure, the URI. It adds work at the cache, the WAF, the proxy and the signature. The result depends on the implementation.

06 Deployment and the decision

An RFC is one thing. A working production path is a different thing. Use this part to answer "how would you deploy it?".

GET, QUERY or POST?

Checklist for each hop

Browser, client

  • Write QUERY in upper case.
  • Expect a preflight for cross-origin calls.
  • Read Location only if the server exposes it.

CDN, cache

  • Key on method, URI, type and content.
  • Normalise only what is safe.
  • If QUERY is not supported, do not store its responses.

WAF

  • Allow QUERY on the correct routes.
  • Examine its body as a POST body.
  • Use the same size limits as POST.

Load balancer, proxy

  • Forward QUERY with its body.
  • Frame the body the same way as the next hop.
  • Test for smuggling with a body.

Framework, application

  • Route QUERY. Answer OPTIONS with Allow.
  • Strict Content-Type: 400, 415, 422.
  • Authorization, validation, cost limits.

Database

  • Parameterised queries only.
  • Timeouts and result limits.

Logs, SIEM

  • Parse the method QUERY.
  • No raw sensitive bodies in logs.

Documentation

  • OpenAPI 3.2.0 has a query operation in the Path Item Object Source OAS 3.2.
  • List the query formats (Accept-Query).

A test plan with curl Analysis

Run these commands through the real production path, not only against the origin. api.example is a placeholder.

# 1. Does the full path pass QUERY with its body? Expect 200.
curl -si -X QUERY https://api.example/contacts -H 'Content-Type: application/json' --data '{"q":"a"}' | head -1
# 2. Discovery. Expect Allow with QUERY, and Accept-Query.
curl -si -X OPTIONS https://api.example/contacts | grep -i '^allow\|^accept-query'
# 3. Strict Content-Type. Expect 415.
curl -si -X QUERY https://api.example/contacts --data 'x' | head -1
# 4. Lower-case method. Expect 400 or 501, never 200.
curl -si -X query https://api.example/contacts -H 'Content-Type: application/json' --data '{}' | head -1
# 5. Cache key. Two bodies that differ in one field must not share a cached response.
curl -si -X QUERY https://api.example/contacts -H 'Content-Type: application/json' --data '{"q":"a","role":"admin"}' | grep -i '^age\|^x-cache'
curl -si -X QUERY https://api.example/contacts -H 'Content-Type: application/json' --data '{"q":"a","role":"user"}' | grep -i '^age\|^x-cache'

A fallback while hops change

App. A.2 says that a client can send a QUERY and expect 405 if the resource does not support it. A client can then send the same content with POST Analysis. Keep the POST route read-only and give it the same controls.

What is known to work

  • Node 24.18 node:http accepts QUERY. curl, fetch() in Node and Python urllib send it Tested.
  • OpenAPI 3.2.0 (September 2025) can describe a QUERY operation Source.
  • For any other product, read its documentation and test it. Do not say "it supports QUERY" without a test.

09 Question bank

Likely questions from the panel, with short answers. Type a word to filter, for example "cache" or "422".

A. HTTP basics

Q-A1. What does "safe" mean in HTTP?

The client does not ask for a change of state on the server (RFC 9110 §9.2.1). Thus caches, prefetchers and crawlers can send the request freely. The server can still log or count the request. Safe describes the intent of the client, not the code of the server.

Q-A2. What does "idempotent" mean? Give a method that is idempotent but not safe.

Many identical requests have the same intended effect as one request (§9.2.2). Thus a client can send it again after a connection fails. PUT and DELETE are idempotent but not safe: they change state, but a second identical request changes nothing more.

Q-A3. Are method names case-sensitive? Why does it matter?

Yes (RFC 9110 §9.1). fetch() changes only six classic names to upper case. With method: 'query' it sends query, and Node 24 replied 400 (Tested). Always write QUERY.

Q-A4. What is the difference between the query component and the QUERY method?

The query component is the part of a URI after ?. It is part of an identifier (RFC 3986 §3.4). The QUERY method sends its input in the body, which RFC 10008 §1.1 calls the "query content". They only share a word.

Q-A5. What is the maximum length of a URI?

HTTP has no maximum. RFC 9110 §4.1 recommends support for at least 8000 octets. Each hop can set its own limit, and the client cannot know these limits (RFC 10008 §1). A server that cannot accept a URI sends 414.

Q-A6. Why does the fragment never appear in server logs?

The browser does not send the fragment to the server. The fragment is processed only by the user agent (RFC 3986 §3.5).

Q-A7. How much does percent-encoding add?

Each encoded character becomes three characters. In the slide 6 example, 12 characters change, and 30 characters of JSON become 54 (Tested with encodeURIComponent()).

Q-A8. Why not just send a body with GET?

RFC 9110 §9.3.1: content in a GET request "has no generally defined semantics", and a client should not send it unless the origin server said that it supports it. RFC 9205 §4.5.1: generic HTTP software will ignore or reject it. If two hops handle that body in different ways, request smuggling becomes possible.

Q-A9. Why not just use POST for queries?

POST does not promise safe or idempotent. A proxy must not send it again automatically, and a cache can reuse a POST response only for a later GET. RFC 9110 §17.9 says that POST for a query "hinders caching and uses an unsafe method for what would otherwise be a safe request". RFC 9205 adds that POST loses the links of GET.

B. RFC 10008

Q-B1. What is RFC 10008, and who wrote it?

"The HTTP QUERY Method", an IETF Standards Track RFC from June 2026. The authors are Julian Reschke (greenbytes), James M. Snell (Cloudflare) and Mike Bishop (Akamai).

Q-B2. What must a QUERY request contain?

Content, and a Content-Type that agrees with it. "Servers MUST fail the request" if Content-Type is missing or inconsistent (§2).

Q-B3. Can the server guess the type when Content-Type is missing?

No. "A server is not allowed to infer a media type from the request content" (§2.1). A missing type gets a 4xx, for example 400.

Q-B4. When does a server send 415, and when 422?

415: the server does not support the media type. It can add Accept-Query to list the supported types. 422: the type is supported and the content is valid, but the server cannot run this query, for example a field of the wrong type (§2.1).

Q-B5. What is Accept-Query?

A new response header (§3). It lists the query formats that a resource accepts. It is a Structured Field List, for example Accept-Query: "application/jsonpath", application/sql;charset="UTF-8". It applies to all URIs with the same path.

Q-B6. What is the difference between Location and Content-Location?

Location (§2.4) identifies the query: a later GET runs it again with no body. Content-Location (§2.3) identifies this result: a later GET returns the stored result. Both can be temporary.

Q-B7. What is the "equivalent resource"?

A resource that answers a GET with the same result as the QUERY (§2.2). The server can give it a URI in Location, but it does not have to.

Q-B8. How do redirects work for QUERY?

301, 302, 307 and 308 keep the QUERY method. The old browser rule that changes POST to GET does not apply. 303 tells the client to send a GET to the new URI (§2.5).

Q-B9. Can caches keep QUERY responses? What is the rule?

Yes. A cache MAY use a QUERY response for later QUERY requests. The cache key MUST include the request content and its metadata. Caches MAY remove differences that do not change the meaning, only for the key (§2.7).

Q-B10. Do conditional and range requests work?

Conditional requests work as for a GET to the equivalent resource, so 304 is possible (§2.6). Range requests work the same as for GET, but they are of little use. The query format should do its own paging (§2.8).

Q-B11. Why "QUERY" and not SEARCH, REPORT or PROPFIND?

Appendix B: those methods come from WebDAV and use a generic XML media type. QUERY gets its meaning only from the content type. The name also maps to the query component of the URI. Early drafts used SEARCH.

Q-B12. Can a QUERY request also have a query component in its URI?

Yes. Its effect is specific to the resource and outside the scope of the RFC (§2).

Q-B13. Is QUERY in the IANA registry?

Yes. The HTTP Method Registry lists QUERY as safe and idempotent (§5.1). Accept-Query is a permanent field with the structured type List (§5.2).

C. Security

Q-C1. Is QUERY more secure than GET?

Not by itself. It keeps the input out of the URI, so fewer logs and headers copy it. A cross-site page cannot send it without a preflight. But bodies can be logged, the cache key is more difficult, signatures need Content-Digest, and every hop must support it. The result depends on the implementation.

Q-C2. Does a body stop the data from being logged?

No. Body logs, WAF and APM tools and TLS-terminating hops can see it. RFC 10008 §4 says that URIs are "more likely" to be logged. QUERY decreases exposure. It does not remove it.

Q-C3. Why is safe not the same as secure?

Safe describes what the client intends. RFC 9110 §9.2.1 says that safety does not prevent harmful behaviour. A safe QUERY can still carry SQL injection, read data that the caller must not see, or use a lot of CPU.

Q-C4. How can a cache leak data with QUERY? Does a real CDN do this?

If the cache key leaves out part of the body, two different queries share one key. Then one user gets another user's results. cache-key.mjs shows it. I do not say that a specific CDN does this. QUERY caching is new code, and the cache papers show that cache and origin disagreements are exploitable.

Q-C5. What is CPDoS, and how is it related?

Cache-poisoned denial of service (Nguyen et al., CCS 2019). An attacker makes the origin send an error with a header that the cache ignores, and the cache keeps that error for all users. For QUERY, any part of the request that the origin uses but the key ignores is the same type of risk (Analysis).

Q-C6. Does a browser always send a preflight for QUERY?

For a cross-origin request, yes. Only GET, HEAD and POST are CORS-safelisted methods (Fetch; RFC 10008 §4). Same-origin requests and non-browser clients have no preflight.

Q-C7. Does QUERY help against CSRF?

Partly. Forms cannot send QUERY, and no-cors rejects it, so a cross-site page needs a successful preflight. Also, QUERY is safe, so it must not change state. But a permissive CORS policy with credentials still lets a page read the results. That is a data leak, not CSRF.

Q-C8. Why must a signature cover Content-Digest?

RFC 9421 does not sign the content directly (§7.2.8). For a QUERY, @query is only ? (§2.2.7). Thus a GET signing policy, copied with no change, covers everything except the query. Sign content-digest, and calculate the digest again at the receiver.

Q-C9. What is request smuggling, and why does a new method matter?

Two hops disagree about where one request ends. The attacker hides a second request inside the first one. A new method with a body is new input for the parsers, and a hop that does not know QUERY can handle its body differently. T-Reqs (CCS 2021) found such differences between real servers.

Q-C10. How can QUERY get around a WAF?

If the WAF examines only GET URIs and POST bodies, a QUERY body goes through with no check. OWASP WSTG-CONF-06 tests this type of method tampering. Add QUERY to the body rules and the size limits.

Q-C11. What is the risk of the stored-query URIs?

Two risks. First, the URI must not contain sensitive parts of the query (§4, SHOULD). Second, my demo uses a counter, so another client can guess a URI and run a query that it did not write (Analysis). Check authorization on each GET, or use an unguessable ID.

D. Code

Q-D1. What does your server do with a missing Content-Type?

It sends 400 with {"error":"Content-Type is required"} (lines 22 to 23). That follows "MUST fail" in §2 (Tested).

Q-D2. Why did method: 'query' fail?

Method names are case-sensitive, and fetch() changes only DELETE, GET, HEAD, OPTIONS, POST and PUT to upper case. It sent query. Node's HTTP parser rejected it with 400 before my handler ran (Tested).

Q-D3. Why does the server limit the body and the results?

A safe method can still be expensive. The 16 KiB body limit protects the memory. The limit of 100 results protects the CPU and the network. Safe is not cheap.

Q-D4. What does cache-key.mjs show?

Two normalisers for the same two queries. canonical sorts the keys and gives two different cache keys, which is correct. lossy drops role and gives the same key for the admin query and the user query (real output on slide 20).

Q-D5. How did you compute the Content-Digest on slide 22?

SHA-256 of the exact body bytes, then Base64: printf '%s' '{"q":"security","limit":10}' | openssl dgst -sha256 -binary | base64. The result matches the slide. The Signature value itself is shortened and is not real.

Q-D6. What would you change in server.mjs for production?

Send 413 for a large body, not 400 (change tested). Send 404 for an unknown stored-query URI. Handle HEAD, so that Accept-Query discovery works (App. A.3). Link stored queries to their owner and check authorization. Give them an expiry time. Check Accept and send 406 when necessary.

Q-D7. RFC 9110 says 501 for an unknown method. Why did Node send 400?

Node's HTTP parser accepts only the method names that it knows. It rejects other names, such as FOO or lower-case query, with 400 before the application sees the request (Tested). The 501 rule is a SHOULD for origin servers.

Q-D8. Can you show the injection on slide 19?

Line 6 puts query.q into the SQL text. A value with a quote, such as ' OR '1'='1, changes the SQL. Lines 7 to 8 send the value as the parameter $1. The method of the request does not change this.

E. Deployment

Q-E1. What must a CDN do to support QUERY?

Forward it with its body. Key the cache on the method, the URI, the content type and the content. Normalise only safe differences. If it cannot do this, it must not store QUERY responses.

Q-E2. What happens if one hop does not support QUERY?

The request fails with 405 or 501, or the hop handles the body in a different way. That can cause request smuggling. A hop that passes QUERY without the controls that it has for POST becomes a bypass.

Q-E3. Should we change all POST searches to QUERY now?

Only where every hop supports it. Test the full path first (part 06). Until then, a read-only POST route with the same controls is a fallback.

Q-E4. How does a client know if a server supports QUERY?

Send OPTIONS and look for QUERY in Allow (App. A.2). Send HEAD and read Accept-Query (App. A.3). Or send a QUERY and expect 405 if it is not supported.

Q-E5. How do you document a QUERY endpoint?

OpenAPI 3.2.0 (September 2025) has a query operation in the Path Item Object. List the request media types, and give the Accept-Query value.

F. Literature and the talk

Q-F1. Why is there no paper about QUERY itself in your review?

I found no peer-reviewed study of RFC 10008 (Crossref and web search, October 2026). The RFC is from June 2026, so this is normal. I reviewed studies of the mechanisms that QUERY uses: caches, parsers and CORS.

Q-F2. Why these four studies?

Each one matches one new risk of QUERY: CPDoS and web cache deception for the cache key, T-Reqs for body parsing, and the CORS study for the preflight. All four are from ACM CCS or USENIX Security.

Q-F3. Where are the other sources, such as Starov or Cha?

In the references. Starov et al. (2016) measured PII leaks through the Referer header. Cha et al. (2020) and Hartig & Pérez (2018) show that queries can be expensive. The slides cite them where they are used.

Q-F4. Did you run the code?

Yes. server.mjs with curl, fetch() and Python urllib, on Node 24.18, curl 8.7.1 and Python 3.14, on 17 October 2026. The outputs on the slides are from those runs.

Q-F5. What is your main recommendation?

Use GET when the query fits in a URI. Use QUERY for a safe query with large or structured input, when every hop supports it. Use POST when the request changes state. Involve the security team from the start.

10 Glossary

Short definitions of the terms in the talk.

APM
Application performance monitoring. A tool that records requests in an application, sometimes with their bodies.
CDN
Content delivery network. Caches near the users.
Content-Digest
A header with a hash of the body (RFC 9530).
CORS
Cross-Origin Resource Sharing. The browser rules for requests to another origin.
CPDoS
Cache-poisoned denial of service. A cache keeps an error page and sends it to all users.
CSRF
Cross-site request forgery. A page makes the browser send a request with the user's cookies.
Equivalent resource
A resource that answers a GET with the same result as a QUERY (RFC 10008 §2.2).
Hop
One system between the client and the origin.
IANA
The organisation that keeps the registries of protocol values, such as HTTP methods.
IDOR
Insecure direct object reference. Access to an object only because its ID is known or guessed.
Idempotent
Repeated requests have the same intended effect as one request.
Normalisation
A change that removes differences with no meaning, for example the order of JSON keys.
Origin (server)
The server that owns the resource.
Origin (browser)
Scheme, host and port of a page, for example https://app.example.
Preflight
An OPTIONS request that the browser sends to ask if a cross-origin request is allowed.
Query component
The part of a URI after ?.
Query content
The body of a QUERY request.
Referer
A request header with the URL of the page that made the request. The spelling is historical.
Request smuggling
An attack where two hops disagree about where a request ends.
Safe
The client does not ask for a change of state.
SIEM
Security information and event management. A system that collects, indexes and keeps logs.
Structured Field
A header with a strict, typed syntax (RFC 9651). Accept-Query is a List.
TLS termination
The point where TLS ends and the hop can read the request in clear text.
WAF
Web application firewall. It examines requests and blocks attacks.
Web cache deception
An attack that makes a cache store a private page as public.
